PagedAttention from scratch

Three pieces let a KV cache survive a churning batch: a block allocator, a gather kernel, and a preemption policy. Built by hand and measured — naive reservation wastes 84.6% of the pool, paging brings it to 2.8%, and my preemption policy won one workload and lost the other.

Balaji Chidambaram · August 2026 · ~9 min read

The last post ended on an admission. I'd built an iteration-level scheduler that re-decided the batch every decode step, and then had it recompute the entire context on every step, because a KV cache didn't fit. The closing section was called "why a KV cache doesn't just drop in." This is the answer.

Everything below is in nanogpt-served, and every number comes from running it.

01The cache that didn't fit

A KV cache is simple when you serve one request: as each token is generated you append its key and value vectors to a growing tensor, so the next step attends over history instead of recomputing it. One sequence, one length, one contiguous block of memory.

Continuous batching breaks all three assumptions at once. Membership changes every step. Lengths differ per request and grow at different rates. A request can finish at step 3 and free its memory in the middle of the pool. There is no single contiguous tensor to append to, which is why my scheduler cheated and recomputed.

That's the smaller problem. The larger one appears the moment you try to fix it the obvious way. You don't know how long a request will run — generation stops on an end-of-sequence token, not a schedule — so the safe move is to reserve the maximum: max_seq_len worth of KV for every admitted request, up front.

Here is what that costs. Three requests that end up using 37, 900, and 12 tokens, with max_seq_len = 2048:

slots actually holding a token slots held but empty
Both bars drawn to the same scale. The three requests need 949 token-slots; naive reservation holds 6,144 to be safe. Six times more memory than the work requires.
Why the waste matters. Decode is memory-bound: at batch size 1 the GPU spends nearly all of a step moving weights out of HBM and almost none of it doing arithmetic. Batching fixes that, because one weight-read serves many requests. But how many you can batch is capped by how many KV caches fit in memory. Waste 84.6% of that memory and you've capped your own throughput at a sixth of what the hardware could do.

02The idea is fifty years old

PagedAttention doesn't invent anything. It recognizes that KV-cache fragmentation is the same problem operating systems solved for RAM in the 1960s, and reuses the solution directly.

A process wants a big contiguous address space. Physical RAM is fragmented. The OS chops memory into fixed-size pages, gives each process a page table mapping its virtual pages to whatever physical frames are free, and puts a piece of hardware — the MMU — in the path of every load and store to walk that table. The process gets its illusion of contiguity; physical memory stays a free-for-all.

Swap four nouns and you have PagedAttention:

Attention needs to read every past key and value. It has no opinion about whether they sit next to each other. Contiguity was an artifact of how the allocator handed out memory, and one level of indirection removes it.

03Part 1 — the allocator

Two objects. A pool owns physical blocks and knows nothing about requests. A block table belongs to one request and knows nothing about other requests. Neither has any idea what a tensor is — the file imports no torch at all, because paging is integer bookkeeping. vLLM draws the same line, which is why its block manager knows nothing about CUDA.

Neither request owns a contiguous run, and nothing in the system cares. Physical block ids carry no ordering information at all — the order lives in the position within block_ids, not in the values. After an hour of real serving a fresh request might hold [91, 12, 400, 7].

Address translation is two integer operations against a list lookup. vLLM uses block size 16 — a power of two — so in the hot path both become a shift and a mask. No division.

The one real decision in the allocator is when to grab a new block:

# LAZY: allocate only when a token has nowhere to go.
def append_token(self):
    # True when the tail block is full — AND when there are no
    # blocks at all. One modulo covers both cases, no special-casing.
    if self.num_tokens % self.pool.block_size == 0:
        blk = self.pool.allocate()
        if blk is None:
            return False          # pool dry — the scheduler's problem now
        self.block_ids.append(blk)
    self.num_tokens += 1
    return True

Lazy allocation caps waste at block_size − 1 per request. Eager — grabbing the next block the instant the tail fills — caps it at block_size, because a request that stops exactly on a block boundary is left holding an empty block it never writes to. One slot of difference, and it only appears in the aligned case.

Two smaller things. allocate() returns None instead of raising, because running out of blocks is a normal operating condition — under load the pool will go dry, and that's a signal to the scheduler, not a crash. And the waste bound is structural: every interior block is full by construction, so all of a request's slack lives in its tail block.

The bound is easy to state and easy to get wrong, so I measured it:

Per-request waste came out [11, 12, 4], all under the bs − 1 = 15 bound. The middle request holds 900 tokens and 900 % 16 = 4, so its tail block is partial by 12.

04Part 2 — the gather

At this point I had a page table with no MMU. translate() would tell you where a token lived, and then nothing went and got it. Attention needs an actual (T, d) matrix — T rows for T tokens of history, d numbers per row — where row i holds the vector for logical position i, whichever physical block it happens to sit in.

Row i is the vector at logical position i — that sentence is the gather's entire job description. Attention downstream never learns the blocks were scattered.

The obvious implementation is the page-table walk drawn T times:

def gather_kv_loop(pool_tensor, table):
    rows = []
    for pos in range(table.num_tokens):
        block, offset = table.translate(pos)     # the page-table walk
        rows.append(pool_tensor[block, offset])  # (d,) one token's vector
    return torch.stack(rows)                    # (T, d)

The vectorized version computes all T addresses at once. The trick is to stop thinking in (block, offset) pairs and give every token a single integer address — flatten the pool from (num_blocks, block_size, d) to (num_blocks · block_size, d), so slot = physical_block · block_size + offset. Once every token has one address, "gather" is one index:

def gather_kv(pool_tensor, table):
    num_blocks, block_size, d = pool_tensor.shape
    T = table.num_tokens

    blocks  = torch.tensor(table.block_ids)      # (L,)  logical order
    base    = blocks * block_size                # (L,)  first slot of each block
    offsets = torch.arange(block_size)           # (block_size,)
    slots   = base[:, None] + offsets            # (L, block_size) via broadcast
    slots   = slots.reshape(-1)[:T]              # (T,)  flatten, drop the tail slack

    flat = pool_tensor.view(num_blocks * block_size, d)
    return flat[slots]                          # (T, d) — one indexing op

Two details here matter. .view raises if the bytes can't be reinterpreted for free; .reshape silently copies. On a multi-gigabyte KV pool read every decode step, I want the one that errors.

And that blind [:T] slice — dropping the unfilled slots of the last block — is only correct because of the invariant from §03. Decode only ever appends, so every interior block is full and all the slack lives in the tail. If decode could write into the middle of history, that line would return garbage silently.

Both versions produce bit-identical output — I checked with torch.equal, not allclose, against a naive contiguous baseline, with the request's blocks deliberately non-consecutive ([0, 2, 3]). max abs diff: 0.00e+00. Then I timed them at realistic size:

29× apart, on identical bytes moved. The loop pays 2,048 round-trips out to the interpreter; the vectorized version runs a fixed handful of operations no matter how long the sequence is.

The 29× itself isn't a PagedAttention result — it's ordinary Python overhead, and anyone who has vectorized a loop before will have guessed the direction. What I hadn't internalized is that a memory-traffic model predicts these two functions cost the same, since both copy exactly T·d numbers. The cost isn't in the copy. It's in the 2,048 separate trips through the interpreter to schedule the copy.

Two things about this implementation would not survive contact with a real GPU. torch.tensor(table.block_ids) rebuilds a tensor from a Python list on every call, with no device placement — on CUDA that's a host-to-device transfer per decode step, which reintroduces exactly the per-step overhead the vectorized version was meant to remove. A real scheduler keeps block tables resident on device and updates them in place.

The bigger problem: the copy shouldn't exist. Materializing a contiguous (T, d) buffer means writing it into HBM and reading it straight back. At T=2048, 32 layers, 64 requests, fp16, that's 2.1 GB gathered per decode step — and since a copy crosses the bus twice, ~4.3 GB of HBM traffic, roughly 1.4 ms at 3 TB/s, spent moving data that was already in HBM. vLLM fuses the gather into the attention kernel so the contiguous copy is never formed. That, not the 29×, is why PagedAttention needed a CUDA kernel and not just a smarter indexing expression.

05Part 3 — what happens when the pool runs dry

Paging bounds the waste; it doesn't create memory. Oversubscribe hard enough and allocate() returns None while a running request needs one more block to take its next step.

My instinct was to reach for the word eviction, and that instinct is wrong. When a CPU cache evicts a line it discards a cold copy — RAM still has the data, nothing is undone, nobody is harmed. A KV pool has no cold blocks and no backing store. Every block belongs to a request that needs it on the next step.

You can't free memory here without hurting someone; you can only choose whom. That's preemption, and it's a policy question, not an implementation detail.

The cost of the choice has a clean formula. Preempting a request means releasing its blocks and putting it back in the queue. Its generated tokens are integers and are never lost — only the KV is. So:

cost(preempt R) = R.prompt_len + R.generated    # tokens to recompute

A resume is a prefill, only longer — so the price of preempting a request rises every step it runs. All of this is CPU-side integer bookkeeping; the scheduler never touches the GPU. It decides who is in the batch and who loses their blocks, while the GPU holds the tensors and runs the kernels. That split is why paged_kv.py imports no torch and paged_attention.py does.

vLLM's real allocator has three tiers, and the one I built is the last of them:

"There are no cold blocks" is true at tier 3, and only at tier 3. Tiers 1 and 2 are where a real server spends most of its time.

The mechanism has a right answer — release the victim's blocks, requeue it, treat the resume as a prefill. The policy has only defensible ones. Mine came from one question: is anything guaranteed to finish? If a request is one token from done, preempting it throws away everything it has built for no gain. So protect whoever is closest to finishing, and preempt whoever has the most left to do:

def select_victim(self, requester):
    # Protect whoever is closest to done; preempt whoever has furthest to go.
    return max(self.running, key=lambda r: r.max_new_tokens - r.generated)

The baseline I put in as a placeholder preempts the most recently scheduled request — roughly what vLLM does, which preempts in reverse order of its running queue. (That's LIFO by scheduling recency, which stops being the same thing as arrival order once a queue exists; my harness approximates it with arrival order.) On five requests and a pool oversubscribed 1.8×, my policy won comfortably:

most-remaining (mine)163242×
newest-arrival (vLLM)1816649×

Then I ran a second workload: steady short traffic with one long request mixed in, 14 requests, oversubscribed 3.5×. It reversed the result.

policy · open workloadstepspreemptionstokens recomputedworst-hit request
most-remaining (mine)233253×

Five times the wasted recompute, and four steps slower. The policy that won the first test loses once the workload includes a request that doesn't look like the others.

There are two structural reasons, and I only understood the first before running this. Cheapest-to-preempt and fairest-to-preempt pull in opposite directions, through a feedback loop: the least-progressed request is always the cheapest victim, and preempting it keeps it the least-progressed, so it stays the cheapest victim. The arm that does this deliberately — cheapest-recompute, evict whoever holds the fewest tokens — posts the best recompute score of all six policies on the closed workload, 13 tokens. It pays for that score with eleven preemptions, five landing on R3 and five on R4, each costing zero recomputed tokens because neither request had produced anything to throw away. Two of five requests spent the run being bounced back to the queue, and the scoreboard called it a win.

The second reason is the one the open workload exposed, and it's about information:

Look at what each policy measures, and who sets that number. Newest-arrival reads arrival time — a field the scheduler has no control over, fixed before the request entered the queue, and unchanged by anything the scheduler decides. Most-remaining reads max_new_tokens - generated, and preempting a request is precisely what stops generated from growing. The decision feeds back into the number the decision is made on. That is why my victim never changed and vLLM's did: a dependent key selects the same request forever, while an independent one lets the winner rotate as new requests arrive.

My key is also cheating. max_new_tokens - generated is remaining budget, not remaining work. Generation stops on an EOS token; max_new_tokens is a ceiling the client asked for, not a prediction. This is shortest-job-first in disguise — provably optimal for mean turnaround time, and dependent on knowing job length in advance, which schedulers never do.

06What's next — and what I got wrong

The state of the build: the allocator, the gather, and the policy all exist and all run, and the scheduler still recomputes. Wiring paged_kv into scheduler.py and benchmarking against the recompute baseline from the last post is the next step. Until that lands this is three components, not a working cache.

Two things I got wrong.

My first comparison harness was broken, and it read as a finding. The initial open workload asked for a request larger than the entire pool, so every policy starved identically and all six tied. Six identical rows looked, for about a minute, like a result: policy doesn't matter. A benchmark where every arm ties is a bug report, not a conclusion.

And the fixed harness still under-discriminates. Three or four preemptions per run is a small sample, and oldest-arrival produces numbers byte-identical to mine on both workloads, which means these workloads don't separate those two policies at all. The tables above are directional. Making them a verdict needs runs long enough for policies to diverge and workloads built so that different victims actually get chosen.

Not covered here, because they're adjacent to the build and not in it: prefix caching and copy-on-write, swap-to-CPU as the alternative to recompute-on-resume, and kernel fusion.

One thing I'd want to know before trusting any of this at scale: my policy assumes preemption is the interesting decision, but tiers 1 and 2 of that allocator — the free list and the prefix cache — are where a production server spends nearly all its time. A better prefix-cache hit rate probably beats any victim-selection policy, and I have no measurement either way.
